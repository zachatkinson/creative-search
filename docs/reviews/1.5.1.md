# 1.5.1 review: HTML entities in indexed text and in the query

Built 27 October 2026 on the branch `release-1.5.1`, a patch release from `main` at v1.5.0. Zach's brief: names stored with entities (`Philly&#8217;s Hoodie` from an import, `Rock &amp; Roll`) were cut into `philly`, `8217` and `amp`, so decode every text and the query in one place, show the names correctly, and rebuild existing indexes. No schema change, no hook added or renamed, no setting, no new string, no floor moved, no dependency.

## What was built

| Item | What | Decision |
| --- | --- | --- |
| One decode | `Domain\Tokenizer::decode()`: `html_entity_decode( ENT_QUOTES \| ENT_HTML5, 'UTF-8' )` repeated until nothing changes; the first step of `Tokenizer::words()`, so every `tokenize()` and `key()` (fields, facts, name and SKU keys, attribute terms, synonyms, query rules) goes through it, and the query parser decodes the query before cutting it into chunks | D-133 |
| What is shown | The indexer writes a document's title and its facts' labels and attribute names decoded, whichever reader or `csearch_document` filter they came from; the panel's scope rows decode their term names. A fact's `value` (the query argument) is untouched | D-133 |
| Rebuild | `Tokenizer::VERSION` 2 → 3: a 1.5.0 index owes one full rebuild through `Reindex::checkAnalysis()` (D-098) | D-133 |

## The seven dimensions

**DRY and SOLID.** One function decodes, in the Domain's tokenizer, which is already the one place text becomes tokens; no reader decodes names on its own. The readers' existing `html_entity_decode()` calls (descriptions, content titles) stay: they also strip tags, and decoding again is a no-op by construction. Display decoding sits where the document is written (the indexer) rather than in each of the three readers.

**Anti-patterns.** No query added and nothing on the search path but one `html_entity_decode()` of the query, a few microseconds. The decode loop has no arbitrary cap: each changing pass removes an `&` or shortens an `&amp;`, so it ends, and the mutant that turns it endless is caught by a timeout. No global state, no new filter.

**Security.** The decoded text is never output raw: the panel builds names as text nodes (`view.js`, "never markup"), and the results page's lines go through `esc_html()` once (`EntitiesTest` asserts `Black &amp; White`, never `&amp;amp;`). Decoding `&lt;script&gt;` yields text the same escaping covers. The title stored in the documents table is written through the repository's `prepare()` as before.

**Accessibility.** The panel now reads "Rock & Roll" instead of "Rock &amp; Roll" to a screen reader. No markup changed.

**Internationalisation.** No string added or changed. `ENT_HTML5` decodes named entities for every script (`&eacute;` folds to `e` as a typed é does), and the decode runs before lower-casing, so a case-sensitive entity name is read as written.

**Testing.**
- Unit: `TokenizerTest` adds `&#8217;`, `&#039;`, `&rsquo;`, `&apos;`, `&amp;`, `&#8211;`, a twice-encoded `&amp;#8217;`, an encoded inch mark and an encoded accent, plus `decode()` itself (three levels of encoding, a bare `AT&T`, decoding twice changes nothing).
- `QueryParserTest` adds an entity apostrophe, an ampersand and `&quot;` phrases.
- The golden test: a product saved as `Philly&#8217;s Hoodie` among the 300-product catalogue is found by "phillys", "Philly's", "Philly’s" and two longer spellings, by name terms only (no prefix, no typo), with exactly the score of the same name stored with a real ’; "8217" finds nothing.
- Integration: `EntitiesTest` saves the product, a category and an attribute value through WooCommerce and WordPress (the stored forms are asserted first), and checks the index rows, `/suggest` for five spellings, the term and scope rows, the results page's ranked ids and its "Matches" line.
- Every new test fails against 1.5.0 except the results-page escaping, which held already and is kept as a guard.

**Performance.** See the gates: the reindex and the 50-query budgets are within noise of 1.5.0. Text without an `&` costs one `html_entity_decode()` call that finds nothing to do.

## Found during the work

- **WordPress stores term names escaped.** `wp_insert_term( 'Rock & Roll' )` saves `Rock &amp; Roll`, so every category, tag or brand with an ampersand had an `amp` term in the index and showed the entity in the panel's term and scope rows. This fix covers both; it was not in the brief's list of symptoms.
- **"phillys" is reported as a stem match** against any Philly's product, with a real apostrophe or an entity. That is how the scorer already records it, and ranking was to stay unchanged, so the golden test compares the entity's score with the real apostrophe's rather than requiring the `exact` label.
