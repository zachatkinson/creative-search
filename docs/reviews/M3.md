# Milestone 3 review: Index

Released in `v0.4.0` with milestone 4 (D-056; there is no `v0.3.0` tag) · 21 October 2026 · the agency's seven-dimension review, the benchmark numbers, the mutation results and the Plugin Check output, as the spec asks of every milestone's pull request. Written by the author, with an independent pass against the spec by a second reviewer (findings and what was done with them below).

## What the milestone was to build

From the spec's milestone table: repositories for documents, terms, postings and trigrams; `Indexer`; the hook set; Action Scheduler jobs; generations and the switch; `wp csearch index`, `reindex`, `status`. Tests that must pass: each hook queues once; a save request runs 0 extra queries; stock flips without re-tokenising; the reindex builds N+1 and switches; cancel; removal decrements `df`. Done when 10,000 products reindex in under 5 minutes on the CI runner and one product indexes in under 50 ms.

All of it is built and tested, plus the milestone 1 review's carry-overs (the upgrade off the front end behind a lock, network activation, the first build queued on activation, the plugin exception class, the gate 1b comment) and the SQL implementation of the Domain's `IndexStore`, so the searcher from milestone 2 already runs against the real tables in the integration suite. One spec deviation is flagged (D-042: the spec gives one name to a job and a filter).

## The seven dimensions

**DRY and SOLID.** One class per concern. The four table repositories own their SQL and nothing else, on a base class that is the only caller of `$wpdb` and accepts only prepared statements; `IndexRepository` composes them into the Domain's `IndexStore` and reads only the live generation. `ProductReader` turns a WooCommerce product into field texts, `TermReader` does the same for categories, tags and brands, `Languages` resolves the `csearch_languages` filter once, `AnalyzerFactory` builds the one tokenizer and analyzer the indexer, the searcher and WP-CLI share. `Indexer` writes and removes documents; `IndexQueue` collects what a request changed and hands it to Action Scheduler; `Reindex` walks generations; the three hook classes only translate WordPress's arguments into calls on those services. Every step of the reindex returns the next job, so the same code runs as jobs and inline under `--inline`. `IndexStore` is bound to `IndexRepository` in the container, the binding the spec's "Elasticsearch adapter after 1.0" would replace.

**Anti-patterns.** No SQL outside the repositories and the installer, no product loaded on the save request, no `date()` (the upgrade lock reads `Support\Clock`), no `suppress_filters` (product pages are read through `wc_get_products()`, the WooCommerce CRUD path the rules require), no `@phpstan-ignore` and no baseline. Hook arguments, stored options and filter results arrive as `mixed` and go through `Support\Cast`, so a plugin passing the wrong type to a hook cannot fatal a request. The job hook names do not collide with any filter (D-042, found by a test, not by inspection). The SKU keys fit the schema without a seventh table or a list column (D-041).

**Security.** No new public surface: the jobs run in Action Scheduler, the hooks take ids, the CLI is the shell's. Every statement is prepared; identifier lists are built from integers only (`Repository::ints()`), string lists from placeholders only (`Repository::strings()`), and the one interpolated operator in `PostingRepository::forTerms()` is one of two literals. Filter results are coerced to their types (`ProductText::fromArray()`), so a filter cannot write a non-integer into an integer column or a 5 MB title (titles are cut to 255 characters, URLs to 1,024, terms to 64). The upgrade lock is an `add_option()` INSERT, atomic in MySQL. Uninstall removes the new lock option, and its fallback list is kept in step by the existing test (which caught the omission). `docs/SECURITY.md` is unchanged: no new route or form.

**Accessibility.** Nothing a person sees yet beyond WP-CLI's plain-text output. Not applicable this release; `docs/A11Y.md` unchanged.

**Internationalisation.** Every document has a language; the site language is the default and `csearch_languages` adds others with their own readers for products and for term names (D-045), tested with a French reader (the French document is stemmed with Snowball's French stemmer: `Planche` gives `planch`). Stop words come from the built-in list per language, the owner's `csearch_stopwords_{lang}` and the `csearch_stop_words` filter, tested. WP-CLI messages are English and not translated, as WP-CLI's own are; there are no other user-facing strings in this milestone.

**Testing.** 43 integration tests run inside WordPress with WooCommerce 11.2.1, writing products through WooCommerce's CRUD from the same catalogue fixture the unit suite indexes in memory (`tests/Support/WooCommerceCatalogue.php`): a variable product's every field reaches the right posting (name, both kinds of SKU, parent category, tag, brand, global and custom attribute values, stock roll-up, hidden flag, price range); a variation indexes its parent; drafts, exclusion and the `csearch_index_product` filter remove documents; reindexing is idempotent and removal decrements `df` with the row kept at 0; each of the six public filters changes what is written; category, tag and brand documents carry their counts and links. Thirteen triggers each queue the product exactly once; unrelated posts and taxonomies queue nothing; a save is spied on with a `query` filter and touches no plugin or Action Scheduler table until shutdown, where it queues one unique job; stock-only saves and direct stock writes flip the flag on the same row with the postings count unchanged; a renamed category reaches its products through the batch job; the reindex builds N+1, switches, fires `csearch_index_switched`, cleans up and restores `df`; it is not started twice; cancel abandons the half-built generation and leaves the live one intact; live saves during a reindex reach both generations; a product whose filter throws is recorded and skipped. The SQL store answers the milestone 2 searcher for an exact name, an exact SKU, a typo, a prefix, an attribute value, the hidden rule and a category suggestion. The CLI commands are tested against a WP-CLI double. Two harness bugs found on the way are fixed in the loader, not the code (WooCommerce's attribute caches outlive a rolled-back test).

**Performance.** The save request adds no query (tested). Indexing one product is one `wc_get_product()`, one `_sku` meta read per variation (no variation objects are loaded), and per language: one document insert, one dictionary lookup, one insert of the missing terms, one trigram insert for new terms only, one `df` increment and the postings in chunks of 500. The searcher's reads use the postings primary key (`term_id` first) and the dictionary's unique key; the SKU-key read is by document id (`KEY document_id`). The reindex rate is flat from 300 to 2,000 products (4.1 and 4.5 ms a product), so the 10,000-product run should land near 45 seconds, a sixth of the budget; the per-product cost is dominated by WooCommerce reading the product and its terms, not by the plugin's writes. Memory at 2,000 products peaked at 352 MB in the test process, which holds every product it created; a reindex job holds one batch of 100.

## Spec review findings

A second reviewer read the milestone against the spec and the matrix before it shipped and reported 21 gaps, five of them serious. Every one was checked against the code (and, for the Action Scheduler and WooCommerce claims, their source) before acting. All but three are fixed in this release, each with a test; the three left are flagged below.

| # | Finding | Done |
| --- | --- | --- |
| 1, 14 | `as_enqueue_async_action( …, unique: true )` ignores arguments before Action Scheduler 4.0, so on WooCommerce 10.0 one product job would block every other and the reindex would refuse its own next batch; in every version it also counts a running job, dropping a save made during that product's job | Fixed: the plugin deduplicates on pending jobs itself (D-043); tested with a running job |
| 2 | Removing several documents decremented a shared term once | Fixed: each term loses the number of removed documents that carried it; tested in two languages and with a batch |
| 3 | The score's `df` counted every language and generation against a per-language `N`, so IDF could go to zero or below | Fixed differently from the suggestion, with no schema change: the searcher counts `df` from the postings it reads for the query's language and the live generation (D-044, D-050). The golden set still holds, and through the API in two languages |
| 4 | The state was read from the request's option cache, so a running batch overwrote a cancel | Fixed: fresh reads past both option caches, cancel in its own option (D-053); tested with the flag written by "another process" |
| 5 | Offset paging skipped a product when one with a lower id left mid-walk | Fixed: keyset walk by id (D-054); tested by trashing a product mid-walk |
| 6 | A quantity change that kept the flag re-tokenised (MySQL counts changed rows, not matched) | Fixed, and a second cause found while testing it: `wc_update_product_stock()` saves with no changed property before its stock hook, which is now recognised; tested by spying on the writes |
| 7 | A cancelled generation's number could be reused while its cleanup waited | Fixed: the next generation is above live, building and cleaning; tested |
| 8 | A reindex whose job chain died stayed "running" forever | Fixed: cancel abandons it at once when no job of its chain waits or runs; tested |
| 9 | A failed document insert attached postings to another document's id | Fixed: the insert throws `PluginException`; tested with a duplicate |
| 10 | Renaming an attribute value or a parent category did not reach the products | Fixed: attribute taxonomies re-queue their products, descendants of a hierarchical term are included; tested |
| 11 | Deleting a term queued one job per product on the admin request | Fixed: jobs of 100; tested |
| 12 | `csearch_fields` had two contracts | Fixed: the spec's meaning (weights) keeps the name, the text filter is `csearch_product_fields` (D-050) |
| 13 | No CI job ran the 10,000-product budget | Fixed: `index-budgets` job in CI, running both timing tests at 10,000 |
| 15 | The WP-CLI inline flush ran before WooCommerce's deferred parent sync, and a later change in the request was lost | Fixed: flush at shutdown priority 20, re-attached after a flush |
| 16 | Uninstall left Action Scheduler rows (unscheduling only cancels) | Fixed: the group's actions of every status are deleted, also in the `uninstall.php` fallback; tested with a completed action |
| 17 | A deleted network site kept its tables; no multisite test | Half fixed: `wpmu_drop_tables` lists the six tables (tested). Network activation and per-site uninstall are not tested, because the wp-env site is single-site |
| 18 | WP-CLI: exit codes, `--format=json`, untranslated messages | Fixed; tested against the WP-CLI double |
| 19 | A queued reindex could not be cancelled; an inline one left a queued start behind | Fixed; tested |
| 20 | D-048 takes the SQL builders out of mutation testing, which the spec asks for | Not fixed: flagged for Zach in D-048 |
| 21 | Test gaps (inline path, new and force-deleted variations, brand, two-language df, cross-process cancel) | Fixed: each has a test; the force-deleted variation test found that its hook queued the variation's own id as well as the parent, now fixed. `admin_init` also fires on `admin-ajax.php`; D-046 now says so |

Also found while fixing these: WordPress caches a missing option as missing, so a cancel written by another process was invisible even after the cache entry was dropped (`Options::fresh()` clears both).

## Decisions taken this milestone

D-041 to D-049 in `docs/DECISIONS.md`: SKU keys as `=`-prefixed dictionary terms; the `csearch_job_` prefix (a spec deviation); one id in memory and one job at shutdown, and how a stock-only save is recognised; one dictionary for all generations; the shape of `csearch_languages`; upgrades on admin requests and WP-CLI behind a lock; timings at 300 and 2,000 products here and 10,000 on CI; WordPress-bound code out of the core Infection run; and the small indexer choices (name key at read time, recency as the object id, boost rules in milestone 4, variation values from the parent, term documents, the token filter seam, job errors recorded, the switch action).

## For Zach

- **D-042 renames the per-product job** from the spec's `csearch_index_product` to `csearch_job_index_product`, because the spec also names the public filter `csearch_index_product` and WordPress cannot hold both under one name. The filter keeps the spec's name.
- **D-048 is a spec deviation:** the SQL builders are not mutation-tested. The integration suite and the grep gates check them; running Infection against the WordPress suite in the container is the way to close it.
- **Multisite is untested:** the tables drop with a deleted site, but network activation and per-site uninstall have no test because wp-env runs a single site.
- **The 10,000-product reindex was not run on this Mac.** Loading 10,000 products and 40,000 variations through WooCommerce takes longer than the tool's ten-minute limit; the reindex itself is extrapolated from the 300- and 2,000-product runs (D-047). The new `index-budgets` CI job runs it.
- **There is no `v0.3.0` tag** (D-056): the review's fixes reached into milestone 4's files, so the two milestones ship together as `v0.4.0`.
- **Milestone 6 was started in parallel** by a second agent, which stopped at a usage limit; its files are in the tree (`src/Block/`, `assets/`, `package.json` scripts) but are not part of this commit and not registered in the container. Milestone 6 resumes after milestones 4 and 5, whose routes it calls.
