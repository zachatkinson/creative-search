# Milestone 5 review: Results page

Released in `v0.6.0` with milestone 6 (D-066; there is no `v0.5.0`) · 21 October 2026 · the seven-dimension review, the gate results and the independent review's findings. Written by the author; a second reviewer read milestones 4 and 5 against the spec before release, and what was done with each finding is below.

## What the milestone was to build

From the spec's milestone table: the results hook (`post__in`, Relevance sort, `posts_search` removed for products), the count, the corrected-query line, the no-results state and fallbacks. Tests: integration tests on the archive query; Playwright on the results page with Kadence and Storefront; the Product Filters blocks composing with the ranked set. Done when the page costs one extra query and the e2e is green on the shop.

Built and tested, with one gap: the Product Filters **blocks** are not exercised by a test. WooCommerce's filter blocks re-run a `WP_Query` with the main query's vars, `post__in` included (read in WooCommerce's source by the reviewer), and the URL filters they write (`product_cat`, `max_price`, attributes) are tested against the ranked set in both the integration suite and the browser on three themes. The classic filter widgets, which count with their own SQL, are made to count the ranked set and tested at the SQL level.

## The seven dimensions

**DRY and SOLID.** `Results\ProductSearch` decides which query is ranked and what WooCommerce's query, filters and widgets see; `Results\ResultsView` owns the words; `Hooks\ResultsHooks` attaches both and makes sure each line prints once. The ranking itself is `SearchService::rankedIds()`, the same call `/search` makes, with the same cleaning of the words (finding 20).

**Anti-patterns.** No template override: WooCommerce's own hooks and block render filters in classic and block themes (D-057). No search on the raw words anywhere (WordPress's clause and `search_terms` cleared). The `ID IN (…)` clauses are built from integers only.

**Security.** Every string in the lines is escaped where it is built; the fallback products are WooCommerce's own shortcode output through `wp_kses_post`. The reviewer found no XSS. The page reads `s`, `lang`, `csearch_exact` and `orderby` from the request, unslashed and sanitised. Hidden products reach the page only through the ranking's own rule (exact SKU, `hidden_by_sku` on).

**Accessibility.** The count line is a `role="status"` paragraph; the corrected line is a sentence with a link whose text is the shopper's words; the no-results state is a list of links and WooCommerce's own product grid. axe-clean on three themes (docs/A11Y.md).

**Internationalisation.** `_n()` for the count, number formatting through `number_format_i18n()`, every string translatable with translator comments; the "search instead" link keeps the page's `lang`.

**Testing.** 15 integration tests: Relevance order, another sort over the same set, category and price filters narrowing the ranked set, other searches left alone, the count and corrected lines, the exact search, no results with categories and fallbacks, the warm query count, block templates, slashed words, empty and feed searches, the count after a filter, hidden-by-SKU on the page, the no-results line once on block themes, the widget SQL, and pagination not re-logged. Browser tests on three themes and three engines.

**Performance.** One extra query on a warm page. Cold pages and no-results pages cost more without a persistent object cache (D-055).
