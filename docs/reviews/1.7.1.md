# 1.7.1 review: ids and the limit as strings of digits

Built 18 November 2026 on the branch `csearch-1.7.1`, a bug fix Zach authorized that day, found by Claude in Cowork in the check of 1.7.0: `csearch_ranked_ids` kept a `product_ids` member only when `is_int()`, and the limit only when `is_int()`, so a plugin passing ids straight from `$wpdb->get_col()`, which returns strings, got an empty answer with no warning. One fix commit, then the release commit. No schema change, no dependency, no public hook renamed, no setting added, no floor moved; no index rebuild is owed.

## What was built

| Item | What | Decision |
| --- | --- | --- |
| Ids and the limit as strings | `Search\CallerSearch::whole()` reads an integer, or a string of digits only (`ctype_digit()`), as an integer; `ids()` keeps those above 0, the first 2,000 different ones; the limit takes the same reading and is clamped to 1 to 500 by `forCaller()` as before | D-164 |
| Release | 1.7.1 in the header, `CSEARCH_VERSION`, readme.txt's Stable tag, package.json, package-lock.json and block.json; CHANGELOG.md, readme.txt, HOOKS.md (`csearch_ranked_ids`), SECURITY.md, D-162's pointer to D-164 | |

`wp_parse_id_list()` was read in the WordPress wp-env installed (7.1.4, `wp-includes/functions.php` line 5065, `absint()` at `wp-includes/load.php` line 1468) and mirrored rather than called: it makes every value a number through `abs( (int) … )`, so `"-3"` would become 3, `"1.5"` 1 and an array 1 (D-164 point 2).

## The seven dimensions

**DRY and SOLID.** One reading of a whole number, `whole()`, used for both the ids and the limit; the bounds stay where they were (`MAX_PRODUCTS` in `ids()`, the clamp in `forCaller()`). `Support\Cast::int()` was not reused: it takes any `is_numeric()` value, which is wider than the brief allows.

**Anti-patterns.** No new argument, no new type in the public signature; the hook still never fails on a bad value. The fix doesn't call `absint()`, so a negative or fractional value can never turn into a real product's id.

**Security.** What reaches SQL is unchanged: positive integers, at most 2,000, in `%d` placeholders (SECURITY.md, v1.7.1).

**Accessibility.** No markup changed.

**Internationalisation.** No string changed.

**Testing.**
- Integration, `ProductScopeTest`: string ids give the same answer as the integers (the whole answer compared); a variation's id as a string counts as its parent; twenty kinds of junk give the empty list's answer with nothing searched; zero and below are no ids; strings and integers share the 2,000 cap, `"5"` and `5` being one id and the 2,001st different id left out.
- Integration, `RankedIdsFilterTest`: `"2"`, `"1"`, `"0"` (at least 1) and `"900"` (at most 500) as limits; thirteen junk limits ignored.
- Red run on 1.7.0's code: the four new tests fail (`test_ids_given_as_strings_are_the_same_ids`: "numeric strings count as their ids", `'ids' => Array ()` where `12, 11` were expected). Deliberate breaks: with the fix reverted the same four fail; with `ctype_digit()` loosened to `is_numeric()` the two junk tests fail (`ignored: "-3"`).

**Performance.** One `ctype_digit()` per id given, at most a few thousand per call; nothing else changed. No benchmark row: the ranking, the SQL and the cache are untouched.

## Not covered, or left to Zach

- **Leading zeros and very long numbers.** `"007"` reads as 7, as WordPress reads it; a string of digits beyond `PHP_INT_MAX` reads as `PHP_INT_MAX`, which matches no product (and as a limit is clamped to 500). Neither is tested as a case of its own; both follow from PHP's cast and are recorded in D-164.
- **A string limit of `"0"`** asks for 1 result, as the integer 0 does, rather than being ignored as junk: a string of digits means what the same integer means. A signed `"-3"` is ignored (500 results) while the integer -3 is clamped to 1; that asymmetry is D-161's integer rule meeting this release's string rule, recorded in D-164.
- **No independent spec review** was run for a one-function fix; the red run, both deliberate breaks and Infection stand in for it.
