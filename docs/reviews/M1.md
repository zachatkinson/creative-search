## The seven dimensions

**DRY and SOLID.** One place for each name: `Support\Tables` builds table names, `Support\Options` holds every option, meta, transient, cache-group and queue-group name, and the uninstaller and the tests read those lists rather than repeating them. The container resolves by type with an interface-binding table so later milestones can swap the index store, the queue and the clock in tests. `src/Domain` is empty and the unit bootstrap's shim file says that a Domain class needing a shim is a WordPress import, which the spec forbids. One concern per class throughout.

**Anti-patterns.** Direct SQL exists only in `src/Install/` (dbDelta and the uninstaller's `DROP TABLE` and transient sweep), all through `$wpdb->prepare()` with `%i` identifiers; PHPCS's `WordPress.DB` sniffs are scoped to allow it there and nowhere else, and the grep gate repeats the rule. No `date()` (gate 3), no transient as a database, no work on activation beyond `dbDelta` and one `add_option`. `Settings` caches the option per request and clamps on read, so a corrupt option never breaks a request.

**Security.** No public surface yet. Every file declares `strict_types`; banned functions and outbound requests are gates; `uninstall.php` is testable through `Install\Uninstaller` and proven to leave nothing (tables, options, transients, meta, Action Scheduler group, cache group); `hidden_by_sku` defaults to `no` so a dealer-only line stays invisible until the owner says otherwise. `docs/SECURITY.md` has the OWASP walk with this tag's column filled.

**Accessibility.** Nothing a person sees yet. The axe helper with the WCAG 2.2 AA tag set is in `tests/e2e/smoke.spec.ts`, scoped the way the block and the admin tabs will use it, and the manual script is written in `docs/A11Y.md` with this release recorded as not applicable.

**Internationalisation.** The three strings that exist (two admin notices and the plugin description) go through the text domain; the POT is generated into `languages/`; PHPCS's I18n sniff is bound to `creative-search`; the catalogue fixture carries French names, descriptions and accented words so the folding and stemming tests in milestone 2 have real text.

**Testing.** Unit tests cover the settings sanitiser case by case (every flag, every range, every list), the container's resolution and failure modes, the clock, the option names, and the generator (determinism across seeds and sizes, unique SKUs, realistic shape, hero collisions). Integration tests prove `dbDelta` idempotence, every column and key the spec names, the uniqueness of the unique keys, the upgrade path, activation, the plugin headers, the HPOS declaration and the uninstall. The golden set is 50 queries covering 24 kinds of rule, validated against the catalogue at 300 and 10,000 products. Infection runs on what the unit suite covers.

**Performance.** The one budget this milestone has is met with two orders of magnitude to spare. The schema is the spec's: postings keyed `(term_id, document_id, field)`, trigrams `(trigram, term_id)`, the documents table carrying everything a suggestion renders, generation columns on documents and postings with a key for batch cleanup. `docs/QUERIES.md` lists the statements and the keys they will use.

## Escaped mutants (23, Infection 0.32)

All in code the unit suite covers; none in a scorer or SQL builder (there are none yet). Each is a mutant that leaves behaviour observably the same for valid input, or a defensive branch only invalid WordPress state reaches.

| Where | Mutator | Why it is acceptable |
| --- | --- | --- |
| `Settings.php:221` `toString()` | UnwrapTrim | `sanitize_text_field()` already trims; the outer `trim()` is belt and braces. Kept for the unit shim, where the shim trims too. |
| `Settings.php:224` | CastString | `is_scalar()` guards the cast; removing it changes nothing for scalars PHP already stringifies. |
| `Settings.php:262` `sanitizeLanguages()` | Continue_ | After a failed `is_scalar()` the next line's `(string)` of an array would notice; a test with an array is in place but PHP 8.5 stringifies `null` and `bool` silently, so the mutant survives for those. |
| `Settings.php:307` `sanitizeIds()` | LogicalOr | `! is_scalar() \|\| ! is_numeric()`: `is_numeric()` already returns false for non-scalars, so either guard alone suffices. |
| `Settings.php:327`, `332` `sanitizeStats()` | PregMatchRemoveCaret/Dollar | Anchors on `^\d{4}-\d{2}-\d{2}$` and `^[a-z_]{1,32}$`; a test with a longer key is cheap and will be added when the stats roll-up lands in milestone 7, where the real producer of these keys exists. |
| `Settings.php:328`, `338` | Continue_, ArrayOneItem | Same method; same plan. |
| `Container.php:102`, `108` `hookables()` | Foreach_, ArrayOneItem | The hookable list is empty in milestone 1, so no mutant of the loop can be observed. Milestone 3 registers the first hookables and these die then. |
| `Container.php:118` | Coalesce | The binding table is empty in milestone 1; same. |
| `Container.php:137`, `141` `build()` | Continue_ | Removing a `continue` after a successful resolution falls through to a `throw`; the tests for scalar defaults and typed dependencies would catch it, except that the mutated path first appends the argument, so the exception message check is what fails. Kept; a stricter assertion on the built instance is in `test_builds_once_and_resolves_dependencies_by_type`. |

## Addendum, 21 October 2026, after the floor change (D-023)

Every gate was rerun on PHP 8.5 with PHPUnit 13.4 and Infection 0.35: PHPCS clean, PHPStan level 9 clean, grep gates clean, unit 78 tests with coverage 95.88 %, Infection MSI 93 %, benchmark 0.4 s, integration 22 of 22 on both legs of the matrix (WordPress 7.1.3 + WooCommerce 11.2.1 and WordPress 7.0.5 + WooCommerce 10.0.6, both on PHP 8.5.12), Plugin Check clean on both, Playwright 10 of 10 on both, Firefox included.

One test flaw surfaced and was fixed. `ActivationTest::test_activation_schedules_nothing_and_indexes_nothing` asked Action Scheduler for *any* action in the plugin's group; the uninstall test cancels, but does not delete, the action it schedules, and WooCommerce's Action Scheduler tables are not among the core tables the WordPress suite reinstalls, so one cancelled action survived per run and the third run failed. The assertion now asks for pending actions, which is what "schedules nothing" means, and `IntegrationTestCase::set_up()` deletes the plugin's group from the Action Scheduler tables before each test, so runs no longer accumulate state. Two consecutive runs are green.


## Second pair of eyes (Claude for Zach, 21 October 2026, against v0.1.0 and the D-023 addendum)

**Verdict: milestone 1 approved.** The skeleton matches the spec's milestone table line for line, the gates are real (a warning fails PHPCS, PHPStan has no baseline, the grep gates and the coverage floor are scripts CI runs), the integration suite proves what the spec asked (`dbDelta` idempotent, every column and key, uniqueness, upgrade, activation that does no work, uninstall that leaves nothing), and the self-review is honest about the escaped mutants. Nothing blocks milestone 2. Four should-fix items, none urgent, each with a milestone to land in:

1. **`Settings::set()` bypasses `sanitize()`** (`src/Settings/Settings.php`). Any caller can store an unclamped or mistyped value; the typed readers clamp some keys on read but not all. Make `set()` run the key through the same rules `sanitize()` uses (or make the settings screen and WP-CLI the only writers and have both call `sanitize()` on the whole array), so a corrupt option can never come from the plugin's own code. Milestone 7, before the settings screen exists; a unit test that `set('retention_days', 9999)` stores 365.
2. **`Schema::maybeUpgrade()` runs on every request** (`src/Plugin.php` boot). Today it is one autoloaded-option read, which is fine; once milestone 3 adds a real upgrade, `dbDelta` would run inside whichever request arrives first after an update, a shopper's included, and two concurrent requests could both run it. Move the upgrade to `admin_init` (and `wp csearch` commands) behind a short lock (a transient set with `add_option`-style atomicity), and show the "index needs a rebuild" notice when an upgrade changes the index tables. Milestone 3, with its first schema change.
3. **Network activation creates the tables on the main site only** (`src/Install/Activator.php` ignores `$network_wide`). Each other site gets its tables on its first request through `maybeUpgrade()`, which is the same front-end `dbDelta` as item 2. Walk the sites on network activation the way `Uninstaller::run()` does. Milestone 3 (same change as 2).
4. **`phpcs.xml` still says `minimum_supported_wp_version` 6.8** while the floor is 7.0 (D-023); PHPCompatibilityWP and the WordPress sniffs use it to decide which deprecations to flag. One-line fix, milestone 2.

Smaller notes, for the record: grep gate 1b catches string-built SQL only when the string is built inside the `$wpdb` call; a query assembled into a variable first passes, so PHPStan and the review carry that rule (fine, but the gate's comment should say so). `Container::build()` throws `InvalidArgumentException` with `esc_html()` on the message, which is right for WordPress output but makes the test assertions on messages brittle; consider a plugin exception class. The Infection scope excludes `src/Install` and `src/Support`, which is right while they are WordPress-bound; `Support\Clock` has no WordPress in it and could join the unit run.

**Spec changes from this milestone, applied to `docs/SPEC.md` and the Claude doc:** the documents table's unique key is `(generation, type, object_id, lang)` and the row carries `total_sales` (D-012, D-013: the spec was wrong, the code is right); and the first index build is queued on activation (one Action Scheduler job, no work on the request) rather than left to the owner to find on a Tools tab, since a search plugin with an empty index until someone reads a settings page is a bad default. `Activator` and its docblock change in milestone 3 to match; the integration test "activation schedules nothing" becomes "activation schedules exactly one build and indexes nothing on the request".

**For Zach:** the five pre-milestone decisions are taken as recorded (D-001 to D-005); the PHP 8.5 and WordPress 7.0 floors (D-023) are yours and stand, with the one consequence D-023 already states: no host below PHP 8.5 can run the plugin, which matters only if it is sold. Nothing on the demo is testable until milestone 3 (the index) and 4 (the routes); milestone 6 is the first thing a shopper sees.
