# Milestone 4 review: Query and API

Released in `v0.4.0` with milestone 3 (D-056) · 21 October 2026 · the agency's seven-dimension review, the benchmark numbers and the gate results. Written by the author. Milestone 3's independent review ran before this milestone was finished; this one has not had a second reader yet, and the findings that review raised about shared code (the store, the queue, the state) are fixed for both.

## What the milestone was to build

From the spec's milestone table: the search repository (the widening plan to one SQL statement), the cache, the rate limiter, `/suggest`, `/search`, `/status`, the log writer, `explain`. Tests that must pass: route schemas, caps, 429s, cache headers, the deferred log write, redaction; the golden set through the API. Done when `/suggest` is within 60 ms warm and 100 ms cold at p95, `/search` within 100 ms, and a call within 4 MB.

All of it is built and tested, plus `POST /click` and the nightly purge and roll-up from the spec's Logging and Analytics sections. One deviation is flagged: the widening plan is not compiled into one SQL statement (D-055); the budgets it was for hold with a wide margin.

## The seven dimensions

**DRY and SOLID.** `Search\SearchService` is the one place a query string becomes a ranked answer; the routes, the results page (milestone 5) and `wp csearch explain` all call it. `Suggestions` turns hits into the panel's rows from the documents table alone, `Cache` and `RateLimiter` are small and separate, `SearchLog` writes after the response, `Clicks` and `LogMaintenance` own their one job each. The four routes share `Args` (the `q` and `lang` schema), `Schemas` and `Responses` (rate limit, cache headers, conditional GET). The Domain searcher is unchanged in shape: the SQL store implements the same `IndexStore` the golden set was proven against in memory.

**Anti-patterns.** No product object is loaded on the search path: name, URL, price, stock and image id come from the documents table, the image through `wp_get_attachment_image_src()`. No answer is computed for a 304. No string-built SQL. The boost rules read term relationships for the candidates only when the owner has rules.

**Security.** Four routes, three public and read-only, one public write (`/click`) that can only set two columns on an existing anonymous log row. Every argument is typed by its schema: `q` sanitised and capped at 200 characters with control characters removed, `lang` a pattern, `limit` 1 to 10, `per_page` 1 to 100, `orderby` an enum, `type` an enum, `id` a positive integer; tested with bad values (400s). `/status` needs `manage_woocommerce` (401 and 403 tested). Rate limits on every public route answer 429 with `Retry-After`. Errors are `WP_Error` with `csearch_` codes and translated messages. The log keeps no identity and redacts the whole query when any part looks personal (tested); the rate limiter hashes the client key with a salt and keeps it in the object cache only. `docs/SECURITY.md` needs its first REST entries before 1.0; noted for milestone 8.

**Accessibility.** Nothing a person sees yet. The routes return what the block needs to announce results (`total`, `corrected`) in milestone 6.

**Internationalisation.** `lang` selects the documents and falls back to the site's language when the shop does not index it; the fallback-language search runs when a language finds nothing (setting, on by default). Prices go through `wc_price()` and `wc_format_price_range()`, so a French page gets French formatting. Error messages and WP-CLI output are translatable, with `_n()` where a count is shown. The golden set's French half passes through the API.

**Testing.** 11 REST tests: answers from the index with every field, empty, long and unknown-language queries, schema rejections and the `OPTIONS` schema, paging, cache headers and the 304, answers cached until a reindex changes the generation, the 429 with `Retry-After` per route and per client, the deferred and redacted log write, clicks, the `/status` capability, hidden-by-SKU and a boost rule changing the order. The golden set runs through `/suggest` and `/search` in both languages with the timing and memory budgets asserted. `explain` is tested through the WP-CLI double.

**Performance.** All four budgets hold by an order of magnitude at 300 products. A cold suggest runs 15 to 18 statements on primary and unique keys (D-055), three of them reading the index state; passing the generation through instead would save two, and merging the two postings reads per level would save a few more, if a shop with a slow database round trip ever needs it. Answers are cached for 60 seconds by generation in the object cache; without a persistent cache that is per request only (D-051), and the rate limit does not hold.

## Decisions taken this milestone

D-050 (`csearch_fields` is the weights), D-051 (cache and rate limit in the object cache only), D-052 (clicks find their row by query), D-055 (several statements per suggest, a spec deviation), D-056 (one release for milestones 3 and 4).

## For Zach

- **D-055 deviates from the spec:** the widening plan is not one SQL statement. The budgets hold at 6 ms cold against 100.
- **D-052 deviates from the spec:** a click carries the query, not the log row's id, because the row is written after the response.
- **D-051:** without a persistent object cache, the rate limit does nothing and answers are not shared between requests. Skatehouse's host should have Redis or Memcached for this to matter.
- **No second reviewer has read this milestone yet.** Running the spec reviewer on it is the first thing to do when milestone 5 is done, or before, if you want the API reviewed on its own.
