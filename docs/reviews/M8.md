## The seven dimensions

**DRY and SOLID.** The language logic stays in `Index\Languages` (one `siteCode()` for the index, the query and the CLI); term counts in `TermReader::count()`; the French run reuses the shared axe helper, which gains one `exempt` parameter rather than a second helper. The matrix's switches live in one place (`tools/integration.sh` and the bootstrap), so a leg runs the same way locally and in CI.

**Anti-patterns.** Nothing hooks translations that WordPress already loads (no `load_plugin_textdomain()`, D-076). No multilingual plugin is installed to test French; a must-use fixture does what skatehouse-core will do (D-080). The one axe exemption is scoped to one rule in one state and argued (D-079), not a blanket disable.

**Security.** No new route, handler or input. The language fallback reads the site's setting, not the visitor's locale (D-076). Translated strings go through the same escaping at the sink, and the i18n check fails a translation whose placeholders differ from the source's. A review finding moved one escape back to the sink (BoostsTab). FiboSearch was installed in wp-env for the benchmark and removed with its options. `composer audit` and `npm audit --omit=dev` are clean.

**Accessibility.** axe on the French panel, results, no-results, every admin tab and the product panel, on three engines and two widths. The run found and fixed three things: Up from the field went to the wrong row, "See all 1 results", and parent categories announced as "(0)". The manual screen-reader pass is **not run** (docs/A11Y.md).

**Internationalisation.** 299 strings, all translated into Canadian French with French typography (no-break space before colons, guillemets). Plurals through `_n()`, including the counts the review found without it; label-and-number forms where several counts share a sentence. The scripts' strings ship as JSON named after the built files (D-084). `composer i18n:check` keeps the POT current and the translation complete.

**Testing.** The French browser spec (14 tests, 70 runs across the five browser projects), integration tests for the site language, the term counts and their re-queue on a visibility change, the translations in PHP and both scripts, the two-form "See all", and the query plans; JS unit tests for the Up key and the singular row. `src/Domain` changed in one place (D-085: the searcher passes the query's key to `IndexStore::documents()`), so Infection was re-run on `Searcher.php`: 156 mutants, all killed (100 %). The rest of the changed code is in `src/Index`, `src/Hooks`, `src/Block` and `src/Repository`, which the integration suite covers and Infection's unit run does not reach.

**Performance.** Every search statement has a key (`QueriesExplainTest`). The 10,000-product budgets were measured for the first time: the reindex passed (99.9 s against 300 s), and the request budgets failed (`/suggest` cold 214 ms, `/search` 209 ms, memory 14.5 MB). Two exact read fixes (D-085) brought the times within budget: `/suggest` cold 81.4 ms, warm 0.4 ms, `/search` 76.9 ms. Memory was 8.41 MB against 4 MB and failed. Zach chose the spec's in-database scoring; with it (D-086) and stored term counts with postings keyed by language and kind (D-087), every 10,000-product budget passes: `/suggest` cold 44.3 ms, `/search` 43.2 ms, 1.69 MB. A reindex now refreshes the statistics of the tables it rewrote, so the plans stay on their keys (D-089). Whole-request time per keystroke is about 100 ms on wp-env, mostly WordPress's bootstrap; a lighter request path (FiboSearch Pro documents SHORTINIT) is a follow-up after 1.0.

## Addendum: ranking in the database (D-086 to D-090)

What changed after the first review, on the branch `scoring-in-sql`:

- **D-086:** products are ranked by one statement in the database. Only a page of results reaches PHP. `explain` keeps the PHP ranking for its breakdown. A parity test holds the two to the same ids, order and totals over about 870 queries.
- **D-087:** schema 2. Term counts are stored per generation and language (`csearch_term_stats`, a seventh table). Postings carry `lang` and `product` under a primary key that leads with them. `csearch_documents` gains `name_key` (approved by Zach).
- **D-088:** `composer infection:sql` runs Infection against the SQL builders inside the tests container.
- **D-089:** a reindex refreshes the statistics of the three tables it rewrote.
- **D-090:** the window between an update and its schema upgrade. Searches read as schema 1 until the upgrade is done, and writes wait. The upgrade runs as a job and under the lock everywhere, resumes when cut off, and records its version only when the tables are complete. The rebuild it owes is not lost to a reindex already running.

### Second independent review (spec-reviewer, on D-086 to D-089)

| # | Finding | Severity | Done |
| --- | --- | --- | --- |
| 1 | Between deploying and upgrading, searches ran the schema 2 statement on schema 1 tables and found nothing | high | schema 1 reads until the upgrade is done; `UpgradeWindowTest` holds the answers identical before, during and after (D-090) |
| 2 | A migration cut off halfway was never retried | high | each step checks itself; the version is recorded only on `Migration::complete()`; `SchemaTest` cuts it off twice (D-090) |
| 3 | Seeding the term counts raced the indexer | high | the indexer waits while an upgrade is due (D-090) |

| 7 | D-089 did not mention MySQL before 8.0.24, where `ANALYZE TABLE` evicts the table definition | low | noted in D-089 |
| 8 | The counts were incremented before the postings were written | low | written after them, in the same write |
| 9 | Docs: "six tables" in `InstallHooks`, no Upgrade Notice, the CHANGELOG cited D-048 for D-088, "keeps answering throughout" was untrue | low | fixed |

A third pass by the same reviewer, on the D-090 code, found four more gaps, all fixed. A request holding a stale cached version could run the migration a second time; it now re-reads the version before and after taking the lock. Starting the owed rebuild settled the debt, so cancelling it lost the rebuild; only a generation going live settles it now. D-090 claimed Action Scheduler retries a refused write; it does not, and the owed rebuild rewrites it. D-090 also named a test that did not exist.

The integration runs found two test-isolation faults, which are fixed. First, an upgrade's DDL committed the lock row, so the lock outlived its test; `IntegrationTestCase` now clears it before each test. Second, the suite's temporary tables are not listed in `information_schema` on MySQL 8.0 or MariaDB 10.6, so the window test now upgrades with real tables.
