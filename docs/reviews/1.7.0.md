Built 18 November 2026 on the branch `csearch-1.7.0-api` from Zach's brief (docs/BRIEF-creative-search-1.7.0.md), for a product configurator first and any plugin after it. ## Spec review

An independent spec review (a fresh agent reading the diff against the brief) found 1 blocker, 3 should-fix and 6 minor:

- **Blocker, fixed.** The benchmark row wasn't in BENCHMARK.md yet: added from the 10,000-product run.
- **Should-fix, fixed.** A caller could pass `source => 'page'` or `'suggest'` and write into the shop's own numbers: those are now logged as `other` (D-163), tested. Sold-out products came back while the shop hides them, unlike the results page: now dropped while `woocommerce_hide_out_of_stock_items` is on, with the option in the cache key (D-161), tested.
- **Should-fix, left to Zach.** The brief says a caller can pass a category scope and product ids together, but its list of arguments has no category. The SQL and the PHP ranking take both and narrow each other (tested through `SearchService::run()`); the filter has no `category` argument, since adding one is a public API choice (D-162).
- **Minor, fixed.** `SearchLog::SHOP` now is `LogRepository::SHOP`, one list. `other` appears once in the menu even when a plugin registers it. The changelog is dated under 1.7.0.
- **Minor, not changed.** "Suggestions clicked" reads 0 on one non-shop source's view (true: clicks belong to the shop's searches). The 500 cap is tested at 2 through `run()`, which proves the limit is filled from the list; the 10,000-product benchmark runs it at 500. The cache key hashes the list before variations are folded; a variation moved to another parent without a new generation could serve a stale answer until the cache's TTL.

## The seven dimensions

**DRY and SOLID.** One engine: the filter reaches the same `searchWith()` and `options()` the results page, the panel and WP-CLI use. The product scope sits beside the category scope in the one ranking statement and the one PHP filter. The hook only attaches; the arguments are read in `CallerSearch`, the logic stays in the service.

**Anti-patterns.** No product object is loaded on the search path: variations are folded by one read of `wp_posts`, stock is the index's. No name, slug or word of the builder or of Skatehouse in the code; `builder` is the brief's generic source name. Tests run on a generic kitchen store.

**Security.** No capability is needed: the answer is ids the results page shows any visitor. Ids and sources reach SQL only as placeholders; ids are positive integers, at most 2,000; a source is one the plugin knows or one registered as 1 to 8 letters (SECURITY.md, v1.7.0).

**Accessibility.** The Analytics tab's new menu has a visible label and sits in the same form as the period; no other markup changed.

**Internationalisation.** Five new strings, translated for fr_CA with its spacing; a registered source's label is a translatable pattern, not concatenated.

**Testing.** `RankedIdsFilterTest` (answer shape, ranking as the page, typos, limit and wrong types, `null` before the index, another answer left alone, pins left out, hidden and sold-out products), `ProductScopeTest` (the scope, variations, empty lists, the cache per list, a category with ids in both rankings, the cap inside the list), `LogSourceTest` (`builder`, `other`, registered sources, the shop's two sources from a caller, the log filter, top queries, chart, totals, completions, roll-up, the menu). Each item's tests failed before its code; each fix had a deliberate-break run.

**Performance.** A shop's own searches cost what they did, plus `source IN` on the log's reads. The filter costs one `COUNT` per call, and on a miss one read of `wp_posts` for a list and one ranking statement with an `IN` list. At 10,000 products, 500 ids: p95 35.7 ms (one word), 40.6 ms (three words).
