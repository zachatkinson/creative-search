# Security checklist

Walked before each tag, by someone other than the author of the milestone. OWASP's top ten mapped to a WordPress plugin, plus the spec's own rules. Each line is ticked with the tag it was walked for and a word on how.

## Rules the code is held to (spec: Security, performance and compatibility)

1. The REST routes are the plugin's only public surface, and they read. `POST /click` writes one log column from a nonce-free beacon and nothing else.
2. Every input is typed by the route schema and cleaned at the edge by the same function the results page uses (`SearchService::clean()`: control characters removed, 200 characters; the parser caps 8 tokens), with allow-lists for `lang`, `orderby`, `type`; the query is only ever output escaped.
3. Every SQL statement is `$wpdb->prepare()`d, identifier lists built from integers only. CI: PHPStan, PHPCS `WordPress.DB`, `tools/gates.sh`.
4. Every admin action checks a nonce and `manage_woocommerce`. WP-CLI commands trust the shell.
5. Output is escaped at the sink: `esc_html`, `esc_attr`, `esc_url`, `wp_kses_post` for price HTML.
6. No user data is serialised; no PHP object is stored anywhere; `unserialize` is banned (gate 2).
7. The log never stores identity: no IP, user id, session, user agent or page URL; queries that look like an email, phone, card or postal code are logged as `[redacted]`.
8. Rate limits on `/suggest` (30 per 10 s) and `/search` (20 per 10 s) per client, counters in the object cache only.
9. No file is written; no remote request is made, except the update check to the agency's own release manifest, which can be turned off (D-140; gate 5 allows that one call and fails on any other).
10. `uninstall.php` removes every table, option, transient, meta, scheduled action and cache entry.

**v1.6.1** (the update check, D-140), walked by the author (docs/reviews/1.6.1.md). A08: the package is installed only from `github.com` over https and only when its SHA-256 matches the manifest (a mismatch tested, and deleted); no code is evaluated from the manifest, whose changelog is escaped. A10: the only request goes to the constant `Updater::MANIFEST_URL` through `wp_safe_remote_get()`, no input reaches the address, and gate 5 fails on any other outbound call. Uninstall also deletes the `csearch_update_manifest` site transient (tested). Plugin Check: no errors or warnings apart from `plugin_updater_detected` for the `Update URI` header, which `tools/plugin-check.sh` allows and nothing else.

**v1.6.2** (D-144), walked by the author with an independent spec review (docs/reviews/1.6.2.md). A08: v1.6.1 checked a package only when the cached manifest named it, so a release published since WordPress's last check, or one met while the manifest was cached as unreadable, installed unchecked. Now every package for this plugin (one of its own releases, or the one WordPress offers for its basename) is installed only when the manifest, read again once when needed, names it and its SHA-256 matches; otherwise `csearch_package_unknown`. Another plugin's package, including the sibling plugins' releases in the same repository, is left alone (tested). A10: the read-again goes to the same constant address through `wp_safe_remote_get()`, only during an install of this plugin's package; gate 5 unchanged.

**v1.6.6** (D-157, D-158), walked by the author with an independent spec review (docs/reviews/1.6.6.md). A03: `ProductIdRepository::carries()` gains a `NOT EXISTS` on the term relationships, its table by `%i` and the visibility term taxonomy id by `%d` (from `wc_get_product_visibility_term_ids()`, cast to an integer), through `$wpdb->prepare()`; the name check reuses `IndexRepository::fieldsOf()` and `termsOf()`, both prepared, with the query's own folded numbers as terms. No new input, argument, outbound request or capability. Item 2 changes translations and a build tool only.

**v1.6.5** (D-154 to D-156), walked by the author with an independent spec review (docs/reviews/1.6.5.md). A03: four new reads (`ProductIdRepository::termsInStock()`, `termsOf()`, `carries()`, `inStockPairs()`) go through `$wpdb->prepare()`, tables by `%i`, the taxonomy by `%s` (an attribute taxonomy the router already checked exists), ids as integers only. A01/A04: the landing's new arguments `csearch_none` and `csearch_near` are signed with `csearch_from` by `wp_hash()`; a changed, added or removed value breaks the signature and the page shows none of them, and each is parsed back to existing `pa_` taxonomies and `sanitize_title()` slugs before use; every string the line prints is escaped where it is built. No new outbound request, no new capability.

**v1.6.4** (D-151), walked by the author. A03: the one new statement (`ProductIdRepository::inStockWithTerms()`) reads WooCommerce's attributes lookup table through `$wpdb->prepare()`, its table name by `%i` and its term ids as integers only; it runs only when WooCommerce itself filters through that table and hides sold-out products. The term filter in the search is a read of postings already loaded.

**v1.6.3** (D-145 to D-149), walked by the author with an independent spec review (docs/reviews/1.6.3.md). A03: the new ranking columns (`lo`, `nd`) and their filter are integers and constant field ids put through `$wpdb->prepare()` with the rest of the statement; no input reaches SQL another way. The panel's "See all" count runs the same `WP_Query` the results-page redirect already ran, with the same sanitised filter slugs. A08: `Updater::tested()` changes only the "Tested up to" value shown and compared by core (a `major.minor` read as the site's maintenance release of that branch); the package check is unchanged. CI (D-148): the release workflow no longer runs CI itself but checks through the API that CI passed on the tagged commit's push to main, with `actions: read` only; publishing still needs `RELEASES_TOKEN`.
